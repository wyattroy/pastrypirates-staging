1. Your two computers

The Blade is home. The Mac is a visitor.

The Blade never moves and never sleeps, so it can hold things. The Mac goes in your bag. So the Mac should never be the only place something lives — it arrives, does its bit, hands it back.

The Blade (Windows)

Home

  • Runs the Watch, all day
  • Runs sea trials (85 minutes each)
  • Anything that must not be interrupted

The Mac

Visitor

  • Thinking, reviewing, talking to Claude
  • Small edits
  • Then push, and walk away

Don’t start a sea trial on the Mac. It takes 85 minutes and you’ll close the lid.

The two machines never talk to each other. GitHub is the only thing they share.

Three rules

1

Bookend every Mac session

Sit down: git pull --rebase  ·  Before the lid closes: git push. If either complains, stop and paste it to Claude. A hook now does the sit-down half for you, automatically. The push half is still yours on purpose — a hook that silently pushed your unreviewed work for you would be its own kind of risk, so it only warns you if you try to close the lid with something unpushed.

2

On the Mac, start Claude with /door

It syncs and asks “can this machine actually publish?” — the check that would have caught 3 September on day one instead of day three.

3

Never close the Mac when git is mid-something

If you see “continue”, “abort” or “rebase in progress”, git is holding the door open waiting for you. That is what stranded your hand-drawn X for three days.

2. One repo, two websites

There is one repo you work in — pastrypirates, cloned on both machines. There are two websites, and reaching each is a different action.

StagingProduction
Addressstaging.playpastrypirates.complaypastrypirates.com
Who’s thereyou, playing work-in-progressreal players
The actiona copy — you publisha merge — you release
The commandnpm run deploy:staginggit merge into main
Approvalnone needed, do it dailyalways yours, live instantly

You never “merge to staging.” Staging is an address, not a branch. That one wrong verb confused Claude for a whole morning.

There is a second GitHub repo, pastrypirates-staging — but it is just a web host that happens to be a git repo, like an FTP folder. Nobody develops in it. Don’t clone it. It exists only because GitHub Pages serves one branch per repo at one address, so a second address needs a second repo.

Production being older than your branch is normal. It is deliberately unreleased. Not a bug, and nobody should alarm you about it.

3. What “HEAD” and “detached HEAD” mean

HEAD is just a label meaning “where I am right now.” Think of the project’s history as a long row of saved snapshots. HEAD is the finger pointing at the one you’re standing on.

Normally HEAD points at a branch name — say claude/cloud-handoff-planning — and the branch points at the newest snapshot. When you commit, the branch moves forward and HEAD comes along with it, still attached. That’s the normal, healthy state.

“Detached HEAD” means the finger is pointing straight at a snapshot instead of at a branch name. You’re standing on a specific moment in history with no branch under your feet.

Why it matters: if you commit while detached, the new snapshot belongs to no branch — so it cannot be pushed, and nobody else can ever see it. The work is real and saved, and it is invisible from every other machine. That is exactly what happened to your Mac: it sat detached for three days holding your drawing, and from the Blade it looked identical to a Mac that had simply done nothing.

How you get detached without meaning to: an interrupted rebase (git steps you through history one snapshot at a time, so mid-rebase you are always detached), or checking out a commit ID directly. The fix is to get back onto a branch — finish the rebase (git rebase --continue) or abandon it (git rebase --abort) — after making sure any commits that exist only there are pushed somewhere safe first.

4. The game itself — what the code is

Vanilla HTML, CSS and JavaScript. No build step, no framework, no bundler. The file in the repo is the file the browser runs. That is why production can move by a plain git merge and why there is nothing to “compile.”

WhereWhat
index.htmlthe page itself — markup and all the CSS
src/engine/the rules of the game. Sailing, battles, trades, the bake-off. Knows nothing about screens
src/ui/everything drawn. The board, the narration box, prompts, the camera, sound
src/net/multiplayer — Firebase, who reads and who writes
src/state/, src/shared/the game’s memory, and the bits both sides need
src/orchestrator.jsthe conductor — runs a voyage turn by turn
assets/, sfx/the art and the sounds
classic/v1, frozen, still playable at /classic

Three ways to play, one game: solo against AI captains, pass-and-play on one device, and a real-time crew game over Firebase. Whether you are host or guest decides who computes — it must never decide what is drawn.

The multiplayer engine is seeded, so the same voyage replays identically. Changing what the engine emits invalidates that whole recorded corpus — which is why fixes are preferred in the drawing layer rather than the rules layer.

5. How anything gets proven before it ships

Three layers, smallest to largest.

The gates
npm test		 141 checks, no browser, about a minute. They read the real files and each one has been proven able to FAIL before being trusted. Run constantly.
The sea trial
node scripts/sea_trial.mjs		 A robot actually plays the game — ten voyages, three modes, three screen sizes, both browser engines, with a real mouse — screenshotting as it goes and running a vision judge over the pictures. 85 minutes. It leaves a report you can open, which is the point: “did you run the sea trial?” can’t be answered vaguely.
The posed pair For “is this drawn wrong?”, the same seeded board photographed before and after. The trial finds a problem; a posed pair settles it.

And four steps, never reordered: show it broken (write the check that fails first) → change it → show that same check pass → sweep. Plus a fresh-context CEO review after every item, whose only question is did the thing you asked for actually happen?

6. The Watch, the Chart, the Glass

How work gets picked up when you aren’t driving.

The Chart.planning/CHART.md — the one plan. Every open job, ranked. Your DO NOW press puts a row at the top
The Inboxyour words, verbatim, the moment you say them. Read before anything else
The Bellon the Blade, every 10 minutes: “is a watch running?” If not, it starts one
The Watcha fresh session that takes one job, proves it, and ends on purpose. Then the Bell rings the next
The Glassyour status page — where you see progress, write ideas, and rule on questions
The ledger.planning/CTO-LEDGER.md — how two machines avoid working on the same thing. They cannot see each other; this is the only place they coordinate

Which sessions can publish a page — and why it kept confusing us

Some Claude sessions can create a shareable page (an “artifact”) and some cannot. It is decided entirely by how the session was started.

How it runsCan publish?
Interactive — you open Claude Code in a terminal and typeYes — and so can any helper it spawns
Headless — Bell watches, scheduled ticks, and Remote ControlNo — and spawning a helper doesn’t rescue it

Remote Control is headless. When you drive the Blade from your Mac it feels like a normal conversation and it isn’t — under the hood it is the same mode the robot watches run in. That is why Claude spent 6 September telling you publishing was impossible while another session had already done it an hour earlier.

So: if you want a page published, use a session you started by typing in a terminal on that machine. Everything else writes the finished page into a queue (.planning/wyclau/PUBLISH-QUEUE.md) and a session that can publish picks it up with node scripts/wyclau/publish_queue.mjs.
